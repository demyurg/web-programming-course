# L5. Как общаются программы

Протокол — общие правила обмена сообщениями между программами. На занятии мы сравниваем способы связи и подробно разбираем HTTP: из чего состоят запрос и ответ, что означает отсутствие подтверждения и почему данные извне нужно проверять. В тренажёре эти идеи применяются при обращении к учебному серверу.

## Задание A5

Развивайте один и тот же тренажёр. Подключите его к предоставленному учебному API через браузерный `fetch`. A5 сдаётся на следующей практике, P6. На P5 проверяется A4 — общие правила изменения и завершения попытки; новая тема L5 и A5 не становятся критериями P5.

## Результат

Пользователь должен загрузить модуль, создать попытку прохождения, сохранять каждый ответ, видеть подтверждение сервера, отправить попытку и получить результат или статус `pending-review`. При перезагрузке клиент использует сохранённый отдельно `attemptId`, чтобы запросить подтверждённую попытку через API. Если идентификатора нет или сервер его больше не находит, интерфейс сообщает, что восстановить подтверждённую попытку нельзя. Полностью сохранять неподтверждённый ввод между перезагрузками не требуется. Локальный ввод не исчезает из-за сетевой ошибки; во время запроса кнопка недоступна, повтор выполняется явно.

Разделите код по обязанностям и файлам. Основные части интерфейса из A2–A4 — список заданий, текущее задание и обзор попытки — оформите как React-компоненты в разных `.tsx`-файлах. Обращения к HTTP API и обработку ответов разместите в отдельном `.ts`-модуле. Типы и правила работы с данными оставьте в TypeScript-модулях вне компонентов: не переносите их в обработчики кнопок или JSX.

Пример организации внутри существующей `trainer/src/`:

```text
App.tsx                      — собирает экран и связывает части
components/TaskList.tsx      — список заданий
components/TaskCard.tsx      — текущее задание и ввод ответа
components/AttemptReview.tsx — обзор попытки
api/trainerApi.ts            — запросы и ответы HTTP API
model/                       — существующие типы и правила A1–A4
```

Внутри обзора и результата можно отдельно оформить отображение одного задания: например, `ReviewItem` показывает ответ, а `ResultItem` — серверный статус и обратную связь. Это полезно, если разметка и данные каждого элемента уже достаточно сложны; отдельные файлы для этих элементов не обязательны.

API также можно разделить подробнее: общий HTTP-запрос и обработку ошибок держать в `api/http.ts`, получение модулей — в `api/sets.ts`, операции с попытками — в `api/attempts.ts`. Один понятный `api/trainerApi.ts` тоже соответствует заданию. Названия и папки могут отличаться, если обязанности остаются разделёнными. Существующие файлы типов и правил не нужно переносить ради совпадения с примером.

## Контракт

Используйте только [контракт API](../../course/CONTRACT.md). Ответы: `{taskId,kind,optionId}` для `single-choice` и `{taskId,kind,text}` для `short-text`. Не заменяйте `taskId` индексом и не добавляйте клиентские поля с оценкой.

Из корня репозитория запустите учебный сервер:

```sh
node course/server/server.mjs
```

Команда одинакова в Linux и Windows PowerShell. Сервер доступен по адресу `http://localhost:3001`. Команду запуска клиента берите из README вашей текущей рабочей версии `trainer`; не добавляйте новую команду только для A5.

## Обязательные сценарии

- отображаются данные модуля из API;
- для обоих видов заданий отправляется корректный Answer;
- PUT заменяет ответ того же `taskId`, DELETE очищает его;
- submit отправляет `{}` и закрывает редактирование;
- `null` отображается как ожидание проверки, а не как ноль;
- HTTP-ошибка или отсутствие соединения видны пользователю, ответ остаётся на экране, есть повтор;
- при работающем сервере перезагрузка позволяет по сохранённому `attemptId` запросить подтверждённую попытку; отсутствие или устаревание id обработано явно;
- Network показывает реальные запросы к API.

## Критерии сдачи

- загрузка модуля и создание попытки;
- правильные PUT/DELETE для ответов обоих видов;
- submit/result и состояния `submitted`/`pending-review`;
- ошибки, повтор и блокировка кнопки;
- список заданий, текущее задание и обзор попытки находятся в отдельных файлах компонентов; HTTP-запросы и обработка ответов — в отдельном TypeScript-модуле, типы и правила — вне компонентов;
- объяснение, как компоненты получают результат запроса и где проходит граница локального и серверного состояния.

Принимаются выполненные сценарии и объяснение реализации. Замечания фиксируются как конкретные доработки. Серверный результат нельзя вычислять и отправлять из клиента как собственный.

## Формат сдачи

Откройте PR из своей рабочей ветки приложения. Укажите SHA, команды запуска клиента и сервера и один проверенный сценарий ошибки. Не перемещайте приложение по папкам.

## Ограничения

Backend, OAuth, React Query, кодогенерация и облачный deploy не требуются. Учебный сервер хранит попытки в памяти: перезапуск удаляет попытки. Назначение вариантов модуля сервером в A5 не требуется.
