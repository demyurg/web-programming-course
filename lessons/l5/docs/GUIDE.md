# L5. Гайд: как программы обмениваются сообщениями

[Задание](../README.md) · [Гайд](GUIDE.md) · [Справка](CHEATSHEET.md) · [Интерактив](interactive.html) · [Слайды](slides-standalone/slides.html)

На L4 мы отделили действие внутри приложения от внешней операции. Когда работу выполняет другая программа, ей нужно отправить понятное сообщение и получить ответ. Эта задача встречается в браузере, настольных и мобильных программах, а также между серверами. Ниже разобраны общие понятия, затем небольшие приёмы на примере списка заметок. Экран тренажёра студент проектирует самостоятельно.

## Протокол и договор конкретного сервиса

Протокол задаёт общие правила обмена: форму сообщений, порядок и смысл ответов. HTTP описывает запрос с адресом, методом, заголовками и иногда телом; ответ содержит статус, заголовки и тело. Конкретный сервис поверх HTTP задаёт собственные адреса, поля и допустимые действия. Клиент должен знать оба договора.

Не смешивайте разные уровни: TCP и UDP передают данные по сети; сокетный API даёт программе доступ к обмену; HTTP задаёт правила запроса и ответа, WebSocket — обмена сообщениями по установленной связи; JSON задаёт способ записи данных; REST — подход к устройству API. Смысл конкретных полей и действий определяет сервис. `fetch` — браузерный интерфейс для запросов, а не протокол. gRPC описывает вызовы и типы между программами и обычно работает поверх HTTP/2. Для A5 выбран HTTP; остальные способы помогают понять этот выбор, но их не нужно реализовывать.

REST организует взаимодействие вокруг ресурсов с адресами и единых правил работы с их представлениями. Полный подход включает больше требований, чем наличие GET/POST/PUT/DELETE и JSON; в частности, ответ может содержать ссылки на дальнейшие действия. Учебный API использует некоторые идеи REST, но в материалах мы называем его HTTP API, не объявляя полностью REST-совместимым.

## Как поддерживают договор API

Описание HTTP API можно вести как обычный текст или в стандартном формате OpenAPI. При подходе «сначала описание» по нему разрабатывают сервер и клиент; при подходе «сначала код» описание получают из реализации. В обоих случаях описание сверяют с работающим сервером. Orval — пример инструмента, который по OpenAPI-описанию создаёт TypeScript-типы и функции клиента. Он не проверяет, что сервер действительно ведёт себя согласно описанию. В A5 источником требований остаётся [Markdown-контракт курса](../../../course/CONTRACT.md); OpenAPI и кодогенерация не требуются.

## Что означает полученный ответ

Ответ со статусом 200 означает успешную обработку HTTP-запроса. Он сам по себе не доказывает, что тело содержит ожидаемые поля. Сбой соединения, HTTP-ответ с ошибочным статусом и некорректное тело — разные случаи. Если ответ вообще не пришёл, клиент не всегда знает, выполнил ли сервер действие: правила безопасного повтора определяет договор сервиса.

## Зачем нужен HTTP-слой

Компонент знает, что пользователь нажал кнопку, но не должен считать ответ сервера подтверждённым только потому, что `fetch` вернул Promise. У запроса есть жизненный цикл: idle, loading, success или error. Сервер остаётся источником истины для сохранённой попытки и результата.

В A5 список заданий, текущее задание и обзор попытки находятся в отдельных файлах компонентов. Типы и правила работы с данными остаются в TypeScript-модулях вне компонентов. Запросы и обработку ответов держите в отдельном TypeScript-модуле: тогда экран работает с результатом операции, а детали HTTP находятся в одном месте. Пример структуры и критерий разделения приведены в [задании](../README.md); имена файлов можно выбрать свои.

Разные файлы помогают увидеть новый для A5 путь: компонент передаёт действие модулю API, тот получает ответ сервера, а интерфейс показывает подтверждённое состояние или ошибку. На защите можно проследить этот путь для одного сохранённого ответа.

Если обзор и результат показывают сведения по каждому заданию, для одного элемента можно выделить отдельный компонент. Обзорный элемент показывает ответ; элемент результата — полученный от сервера статус и обратную связь. Задание и элемент результата связываются по `taskId`, а `score: null` остаётся ожиданием проверки. Общую часть отображения имеет смысл выделять только там, где она действительно повторяется. Это вариант дальнейшей декомпозиции, а не дополнительный критерий A5.

```ts
async function loadNote(id: string): Promise<unknown> {
  const response = await fetch(`/api/notes/${id}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}
```

`fetch` отклоняет Promise обычно при проблеме сети, но 400 или 500 нужно проверять через `response.ok`. Тело JSON читается отдельно. Значение извне имеет тип `unknown`, пока программа не проверила его форму во время выполнения; приведение типа `as Note` само по себе такой проверки не делает.

Путь `/api/...` в примере отсчитывается от адреса открытой страницы. Учебный API A5 работает на `http://localhost:3001`; если клиент запущен на другом адресе, запрос должен быть направлен именно к API.

## JSON-запрос

```ts
await fetch('/api/notes', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ text: 'наблюдение' }),
});
```

В A5 путь, метод и тело берите из контракта. Не переносите пример `/api/notes` в тренажёр.

## Состояния запроса

```ts
type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success' }
  | { status: 'error'; message: string };
```

Состояние запроса позволяет отличить ожидание от подтверждённого результата и ошибки. Поле с введённым ответом и результат операции имеют разный смысл: неудача запроса не отменяет то, что человек уже ввёл.

## PUT и DELETE

В учебном API PUT сохраняет или заменяет ответ задания. Идентификатор задания находится и в URL, и в JSON; они должны совпадать. DELETE очищает ответ. Повторное DELETE допустимо.

## Submit и result

Submit переводит попытку в submitted, а не «считает оценку в браузере». Если непустой short-text ждёт преподавателя, общий status — pending-review, а score — null. Такой результат нужно подписать как ожидание.

## Перезагрузка и попытка сервера

Чтобы после обновления страницы снова получить подтверждённые ответы, сохраните отдельно `attemptId` и запросите по нему `GET /api/attempts/:id`. Идентификатор только указывает, какую попытку запросить; сами ответы приходят от сервера. Если id отсутствует или сервер его не находит, сообщите, что восстановить подтверждённую попытку нельзя, и предложите начать новую. Учебный сервер хранит попытки в памяти, поэтому после его перезапуска прежний id перестанет находиться. A5 не требует сохранять весь неподтверждённый ввод в браузере.

## Ошибка и повтор

Добавьте к учебному запросу `X-Demo-Fail: 1`: сервер вернёт 500 без изменения данных. Проверьте, что поле осталось видимым, ошибка объяснена, повтор без заголовка выполняется одной кнопкой. Не делайте бесконечный автоматический retry.

## Network

DevTools → Network: рассмотрите Request Method, URL, Request Payload, Status и Response. Сверяйте taskId, kind и optionId/text. Network наблюдает факт и не добавляет новых полей.
