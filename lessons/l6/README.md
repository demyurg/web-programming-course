# L6. Как искать ошибки и проверять исправления

## Зачем эта тема

После подключения к API приложение состоит из частей, которые работают вместе. Неожиданный результат ещё не объясняет, какая часть дала сбой. Мы учимся отделять факт от догадки, повторять ситуацию, проверять предположения и выбирать, что исправлять первым. Эти способы полезны в браузере, настольной программе, мобильном приложении и при обмене данными между системами.

Проверка поведения помогает убедиться, что исправление сохранилось после следующей правки. В нашем стеке для автоматических проверок можно использовать Vitest и React Testing Library. На последней встрече цель шире: запустить свой тренажёр и пройти в нём задания преподавателя.

Термины:

- **наблюдение** — что произошло в программе и при каких условиях;
- **гипотеза** — возможное объяснение наблюдения, которое ещё нужно проверить;
- **граница** — место, где одна часть системы передаёт данные другой;
- **повторяемая проверка** — известные входные данные, действие и ожидаемый результат;
- **регрессия** — возвращение уже исправленного нарушения после изменения программы.

## Задание A6: подготовить тренажёр к полному прохождению

**Ожидаемый результат:** в работающем `trainer` человек вводит адрес API и код, видит доступные ему модули, выбирает один и проходит его задания до результата от сервера. После обновления страницы подтверждённая попытка продолжается. Ошибка запроса не уничтожает введённый ответ и не выглядит как успешное сохранение. Работа сопровождается собственным ручным сценарием и тремя небольшими автоматическими тестами.

Перед работой получите актуальные материалы курса в свою ветку A6 из настроенного `upstream`: новая версия учебного сервера содержит каталог доступных модулей. Команды одинаковы в Linux и Windows PowerShell:

```sh
git fetch upstream main
git merge upstream/main
```

Продолжайте от своей рабочей версии A5 и сохраните собственный код в `trainer/` при разрешении возможных конфликтов. Настройка `upstream` описана в [гайде по Git](../../docs/GITHUB_GUIDE.md). Если при подключении учебный сервер отвечает `404` на `/api/available-sets`, проверьте, что в вашей ветке есть опубликованная версия сервера A6.

Развивайте ту же рабочую версию `trainer` после подключения к учебному API. К последней встрече приложение должно выполнять полный путь с **выбранным модулем**, полученным от сервера: показать его задания, дать ответить на поддерживаемые виды заданий, сохранить ответы, завершить попытку и показать результат. Данные заданий, идентификаторы и правильные ответы нельзя подставлять из учебного примера вместо ответа сервера.

В работающем приложении нужен экран подключения: адрес API (по умолчанию `http://localhost:3001`), код доступа и действие «Подключиться». Адрес можно изменить в интерфейсе без правки исходников, изменения конфигурации Vite и пересборки. По введённому адресу и коду приложение получает список доступных модулей. До запуска показывайте только их названия и число заданий: сложность видна из названия, условия заданий ещё не раскрыты. Пользователь выбирает один модуль и запускает попытку. Способ выбора в интерфейсе определите самостоятельно; при одном доступном модуле его тоже можно запустить. Код передаётся в заголовке `X-Access-Code` каждого запроса к выбранному API.

При повторном подключении приложение использует указатель на текущую попытку, если сервер его вернул, и читает подтверждённое состояние. Если попытку по этому указателю прочитать не удалось, покажите ошибку: новую попытку нельзя выдавать за продолжение прежней. Для A6 достаточно одного полного прохождения; после завершения покажите подтверждённый результат. При смене сервера данные прежней попытки не выдаются за данные нового сервера.

Сначала проверьте путь на учебном локальном сервере с открытым кодом `DEMO-A6` и двумя модулями разной сложности. На контрольном сервере каждому студенту доступен свой список модулей; выбор одного запускает единственную контрольную попытку. Адрес сервера преподавателя и персональный временный код будут сообщены отдельно. Не реализуйте backend, выдачу кодов или генератор QR. Форматы запросов, ответов и ошибок приведены в [контракте курса](../../course/CONTRACT.md).

Сбой запроса не должен стирать введённый ответ или превращаться в ложное сообщение об успешном сохранении. Пользователь видит ошибку и может повторить действие. Приоритет при доработке — ошибки, мешающие пройти модуль или искажающие результат. Известные ограничения, которые не мешают основному пути, опишите в README проекта.

История всех попыток, восстановление неподтверждённого ввода после закрытия браузера и автоматическое обновление доступа не требуются.

## Проверки поведения

Для полного пути подготовьте воспроизводимый ручной сценарий: исходные условия, действия, ожидаемый и фактический результат. Если обнаружили дефект, укажите проверенную причину и как подтвердили исправление. Если дефект не найден, опишите проверенный пограничный случай и его результат.

Перед сдачей проверьте полный путь на учебном сервере: подключение, выбор модуля, ответы, продолжение попытки после обновления страницы и результат. Зафиксируйте ожидаемое и фактическое поведение. Отдельно проверьте, что после ошибки сохранения введённый ответ остаётся доступен для повторной отправки.

Выбирайте сценарий, который защищает важное для пользователя поведение вашей версии тренажёра: возможность продолжить прохождение, сохранность ответа или достоверность результата. Сформулируйте, что человек увидит при нарушении, и можно ли повторить ситуацию с известными входными данными. Не требуется искать непременно новый дефект или проверять каждый экран. Случай из лекционного показа про `null` и `0` сам по себе не заменяет проверку поведения вашего приложения.

После устранения препятствий основному пути **напишите три небольших автоматических теста с разным охватом**:

1. Проверка типизированного правила без React. Можно выбрать изменение ответа, запрет изменения завершённой попытки, расчёт прогресса или другое значимое правило вашей модели.
2. Проверка видимого поведения одной части нового интерфейса A6: экрана подключения или списка модулей. Выберите одно состояние или реакцию на заданные в тесте данные.
3. Проверка короткого взаимодействия частей нового интерфейса: введённый код оказывается в заголовке сформированного запроса доступных модулей, а после выбора модуля тот же код передаётся при создании попытки. Тело второго запроса содержит `setId` именно выбранного модуля. Список и начало попытки отображаются по заданным в тесте ответам API.

Каждый тест должен обнаружить конкретное нарушение, а не проверять наличие случайного CSS-класса или снимок всей страницы. В PR для трёх тестов назовите нарушение, которое сделало бы их красными, и что они не проверяют. **Автоматизировать весь путь тренажёра не требуется:** полный проход проверяется отдельно на учебном сервере. Для теста нового интерфейса задайте ответы API в тестовой среде; реальную связь с сервером и заголовок при сохранении ответа и завершении попытки проверяйте отдельно в Network.

[Гайд](docs/GUIDE.md) объясняет уровни проверок и подключение Vitest/RTL к существующему проекту. До L6 команда `npm test` не была обязательной; для A6 настройте её и запустите три своих теста.

## Проверка и сдача

Из `trainer/` выполните проверку типов, тесты и сборку. Команды одинаковы в Linux и Windows PowerShell:

```sh
npm run check
npm run build
npm test
```

Все три команды должны выполняться в вашей рабочей версии `trainer`. Для локального API из корня репозитория выполните, одинаково в обеих системах:

```sh
node course/server/server.mjs
```

В PR укажите SHA, команды запуска приложения, выбранный открытый модуль, условия и результат своего полного прохождения на учебном сервере, а также оставшиеся ограничения. На ближайшей практике проверяется уже выданная работа по подключению API. Это задание выполняется после лекции и рассматривается на последней практике.

При защите отдельно показываются:

- **работа приложения:** полный путь от серверного модуля до результата, включая понятное поведение при ошибке;
- **понимание проверок:** какой сбой обнаруживает выбранный сценарий и чего он не доказывает;
- **три автоматических теста:** их запуск, проверяемое поведение каждого и граница проверки.

На последней практике студенты проходят задания преподавателя в своём тренажёре. Результат тестирования знаний и оценка приложения учитываются раздельно; при техническом сбое предусмотрен резервный способ пройти задания.
