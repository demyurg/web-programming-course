## От сбоя к проверке

**Факт:** что увидели и при каких условиях. **Гипотеза:** возможная причина, ещё не подтверждённая. **Граница:** где данные переходят между частями программы. Сначала повторите ситуацию и найдите наблюдение, которое различит возможные причины. Если сбой пока не повторяется, сохраните условия для следующего случая.

После исправления повторите исходный и соседний сценарии. Проверка связывает известный вход, действие и ожидаемый результат. Потерю ответа или неверный итог исправляют прежде мелкого дефекта оформления с известным обходом; отложенное ограничение записывают явно.

Vitest запускает автоматические проверки, RTL проверяет React через доступный интерфейс, mock задаёт ответ внешней зависимости, а cleanup изолирует DOM между тестами. Подмена API проверяет реакцию клиента; настоящий сервер проверяют отдельно.

До L6 `npm test` не обязателен. После того как основной путь приложения работает, зависимости можно подключить к существующему `trainer`:

```sh
npm install vitest@4.1.12 jsdom@26.1.0 @testing-library/dom@10.4.1 @testing-library/jest-dom@6.6.3 @testing-library/react@16.3.3 @testing-library/user-event@14.6.7 --save-dev --save-exact
npm pkg set "scripts.test=vitest run"
```

Команды одинаковы в Linux и Windows PowerShell. Перед установкой проверьте `node --version`: для Vitest 4.1.12 нужен Node.js 20, 22 либо 24 и новее; Vite 8 требует не ниже Node.js 20.19 или 22.12. `--save-exact` сохраняет точные версии.

## Конфигурация

В `vite.config.ts` используйте `defineConfig` из `vitest/config`, сохраните React-плагин и добавьте тестовую секцию:

```ts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    globals: false,
    setupFiles: "./src/test-setup.ts",
  },
});
```

В `src/test-setup.ts`:

```ts
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(cleanup);
```

При `globals: false` в каждом тесте явно импортируйте `describe`, `it`/`test` и `expect` из `vitest`. `afterEach(cleanup)` нужен, чтобы DOM одного теста не влиял на другой.

## Unit и RTL на стороннем примере

```ts
import { describe, expect, it } from "vitest";

it("считает пробельную строку пустой", () => {
  expect("  ".trim().length > 0).toBe(false);
});
```

```tsx
const user = userEvent.setup();
render(<NoteForm />);
await user.click(screen.getByRole("button", { name: /добавить/i }));
expect(screen.getByText("Новая заметка")).toBeInTheDocument();
```

Примеры относятся к форме заметок/списку покупок, а не к тренажёру. Ищите role/name → label → text, не CSS-индекс.

## К последней встрече

- адрес API меняется в работающем интерфейсе: начальное значение `http://localhost:3001`, на встрече — адрес преподавателя;
- код доступа идёт в заголовке `X-Access-Code` каждого запроса; учебный код — `DEMO-A6`;
- приложение показывает доступные модули по названию и числу заданий, запускает выбранный и продолжает текущую попытку с закреплёнными заданиями;
- ответы сохраняются, попытка завершается, результат показывается по ответу сервера;
- при ошибке введённое не исчезает и успех не объявляется без подтверждения;
- повторяемая проверка показывает, какое важное поведение защищено и чего она не доказывает;
- три автоматических теста проверяют разные части: правило без React, одно состояние нового интерфейса и связь ввода кода с запросами модулей и попытки.

Полный путь на учебном сервере проверьте вручную и запишите исходные условия, действия, ожидаемый и фактический результат. Автоматический сквозной тест не нужен. История всех попыток, генератор кодов и реализация сервера не входят в задание.

**Как выбрать сценарий:** он касается важного пользовательского действия, имеет известные вход и ожидаемый результат, а нарушение можно заметить и повторить. Если дефекта нет, подойдёт проверенный пограничный случай вашей реализации.
