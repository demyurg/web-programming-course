# Гайд L6: ищем ошибки и проверяем исправления

[Задание](../README.md) · [Гайд](GUIDE.md) · [Справка](CHEATSHEET.md) · [Интерактив](interactive.html) · [Слайды](slides-standalone/slides.html)

Примеры используют настольный редактор и форму заметки, чтобы отделить общий способ поиска ошибки от инструментов React. К последней встрече тот же способ пригодится для проверки полного прохождения модуля в тренажёре.

## От неожиданного результата к причине

После отправки запроса ответ может не прийти, хотя сервер выполнил действие. Это **неопределённый результат внешней операции**, а не доказательство ошибки в коде. Сначала выясните, что наблюдается: что было введено, какой запрос отправлен, какой ответ получен или не получен, что показывает интерфейс. Затем отделите предположение о причине от этих фактов.

В настольном редакторе пустое поле после возврата к документу может означать, что текст исчез из данных, выбран другой документ или экран не показал имеющийся текст. Разные объяснения требуют разных проверок. Повторите сбой на известных данных; если он пока не повторяется, сохраните условия и решите, какое наблюдение понадобится при следующем случае.

Декомпозиция помогает задать точные вопросы. Для редактора это данные документа, выбранный документ, отображение и сохранение. Для пакетного импорта — входной файл, разбор записей, запись результата и отчёт. Граница между частями показывает, где ожидание впервые расходится с фактом. Речь идёт об обязанностях частей, а не о числе файлов.

## Что исправлять первым

Сравните последствия для основного действия. Если человек не может сохранить ответ или видит неверный итог, проблема важнее мелкого дефекта оформления с понятным обходом. Учитывайте, как часто сбой возникает и можно ли продолжить работу. Отложенное ограничение запишите явно. После исправления повторите исходный сценарий и соседний случай: исчезновение симптома само по себе ещё не доказывает, что причина устранена.

## Подключение к учебному и преподавательскому API

На компьютере студента `localhost` означает этот же компьютер. Сервер преподавателя будет находиться по адресу в локальной сети. В A6 адрес меняется в уже работающем интерфейсе: сборка проекта и перезапуск Vite для перехода на другой API не нужны. Начальное значение — `http://localhost:3001`. При смене адреса данные и код прежнего сервера не должны смешиваться с данными нового.

Код доступа вводится на экране подключения. Первый запрос `GET /api/available-sets` с заголовком `X-Access-Code` возвращает доступные модули и `currentAttemptId` — указатель на последнюю попытку или `null`. До старта видны только названия и число заданий; название помогает выбрать сложность. Код передаётся и в остальных запросах к выбранному API. Учебный код `DEMO-A6` открыт; персональные временные коды выдаются отдельно для контрольного сервера. Не записывайте их в исходники или файлы проекта.

При старте выбранного модуля сервер создаёт Attempt с `setId` и `tasks`. При продолжении попытки состав берётся из её ответа, а не восстанавливается из каталога модулей. Если сервер дал `currentAttemptId`, но чтение попытки завершилось ошибкой, нельзя показывать новую пустую попытку как восстановленную. Завершённая попытка открывается с результатом; повторное прохождение другого модуля в A6 не требуется. Сервер может предложить один модуль или несколько. После ответа `401` код нужно ввести заново; при отсутствии соединения сначала проверьте адрес и доступность сервера. Это разные наблюдения. Приложение должно показывать ошибку, не теряя уже введённый ответ.

Маршруты и форматы приведены в [контракте курса](../../../course/CONTRACT.md). Проверка с подменённым ответом не подтверждает, что настоящий сервер доступен. Для браузера запросы к другому адресу разрешает сервер через CORS; настройки браузера и режим `no-cors` не заменяют правильный ответ API.

## Зачем тесты

Воспроизведение сбоя — уже первая повторяемая проверка. Автоматический тест сохраняет её для следующих изменений: известные данные → действие → ожидаемый результат. Это полезнее проверки случайного класса или внутреннего имени состояния. Проверка чистого правила, интерфейса с подменённым API и полного пути через настоящий сервер отвечают на разные вопросы и дополняют друг друга.

Термины:

- **Vitest** — тестовый раннер и API ожиданий;
- **React Testing Library (RTL)** — рендер и запросы к DOM через пользовательские границы;
- **jsdom** — тестовое DOM-окружение Node.js;
- **mock** — управляемая замена внешней зависимости;
- **setup-файл** — код, который запускается до тестов;
- **cleanup** — удаление отрендеренного DOM после теста.

## Подключение Vitest и RTL к существующему проекту

Перед L6 проект `trainer` уже должен быть вашей рабочей версией после предыдущих этапов. Не создавайте новый проект и не заменяйте исходники. Если `npm test` раньше не запускался, это нормально: runner и RTL подключаются на этом этапе после готовности основного сценария.

Перед установкой проверьте `node --version`. Для приведённой версии Vitest нужен Node.js 20, 22 либо 24 и новее; если проект использует Vite 8, требуется не ниже Node.js 20.19 или 22.12. Node.js 18 не подходит. Команда проверки версии одинакова в Linux и PowerShell.

Из `trainer/`, одинаково в Linux и Windows PowerShell:

```sh
npm install vitest@4.1.12 jsdom@26.1.0 @testing-library/dom@10.4.1 @testing-library/jest-dom@6.6.3 @testing-library/react@16.3.3 @testing-library/user-event@14.6.7 --save-dev --save-exact
npm pkg set "scripts.test=vitest run"
```

`vitest` запускает проверки, `jsdom` даёт DOM, `@testing-library/react` рендерит React, `@testing-library/dom` предоставляет DOM-запросы, `jest-dom` добавляет читаемые matchers, а `user-event` моделирует действия пользователя. `--save-exact` сохраняет выбранные версии без `^`; lockfile обновляется в том же проекте.

Обновите существующий `vite.config.ts`, заменив импорт `defineConfig` из `vite` на импорт из `vitest/config`, и добавьте React-плагин и тестовую секцию:

```ts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    globals: false,
    setupFiles: "./src/test-setup.ts",
  },
});
```

Секция `test` находится рядом с `plugins`. Создайте `src/test-setup.ts`:

```ts
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(cleanup);
```

При `globals: false` функции `describe`, `it`, `test` и `expect` не появляются глобально: импортируйте их в каждом тестовом файле:

```ts
import { describe, expect, it } from "vitest";
```

Явный `afterEach(cleanup)` обязателен для изоляции RTL-тестов в этом варианте настройки. Без него DOM предыдущего теста может остаться в `document` и сделать следующий тест зависимым от порядка запуска. Не полагайтесь на случайное поведение среды.

## Scripts и запуск

Скрипт `test` — это команда проекта, поэтому `npm test` запускает одноразовый прогон `vitest run`. Для A6 проверяйте его вместе с типами и сборкой:

```sh
npm run check
npm test
npm run build
```

Команды одинаковы в Linux и Windows PowerShell. Режим watch можно добавить отдельным script по документации Vitest; для воспроизводимого результата нужен одноразовый запуск. Автоматические тесты с подменённой сетью не должны требовать запущенного API. Полный путь с настоящим API проверяется отдельно.

## Сначала сформулируйте правило

Фраза «компонент работает» слишком расплывчата. Сценарий для списка покупок точнее: пользователь вводит название, нажимает «Добавить» и видит его в списке; пустой или пробельный ввод не добавляется. Один тест отвечает на один вопрос.

Для своего тренажёра сначала назовите пользовательское обещание, которое важно сохранить: можно продолжить попытку, введённое не пропадает, подтверждение сервера отражено честно, результат показан без подмены смысла. Затем ищите ситуацию, где нарушение этого обещания было бы заметно и где известны вход, действие и ожидаемое наблюдение. Отдельно скажите, чего выбранный сценарий не проверяет. Это ориентиры для выбора, а не требование покрыть весь список.

В A6 нужны три небольших теста с разным охватом. Первый проверяет ваше правило на данных без React. Второй — видимое поведение экрана подключения или списка модулей. Третий связывает ввод кода, получение модулей и запуск выбранного модуля: в запросах должен использоваться введённый код, а интерфейс должен показать данные из заданных в тесте ответов API. Это проверка части клиентского пути, а не полного сетевого прохождения. Путь от подключения до результата проверьте вручную на учебном сервере и запишите собственный сценарий.

## Unit-тест чистого правила

```ts
import { describe, expect, it } from "vitest";

function isFilled(value: string): boolean {
  return value.trim().length > 0;
}

describe("isFilled", () => {
  it("считает пробелы пустым вводом", () => {
    expect(isFilled("  ")).toBe(false);
  });
});
```

Такой тест не зависит от DOM, сети и часов. В A6 выбирайте правило по значению для своего приложения, а не по сходству с этим примером.

## RTL проверяет границу пользователя

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

const user = userEvent.setup();
render(<NoteForm />);
await user.type(screen.getByRole("textbox", { name: /текст/i }), "Проверить API");
await user.click(screen.getByRole("button", { name: /добавить/i }));
expect(screen.getByText("Проверить API")).toBeInTheDocument();
```

Ищите доступные элементы через роль и имя, label или текст. `user-event` асинхронен, поэтому действия ожидаются через `await`. В реальном тесте поместите этот сценарий внутрь `it` или `test` и импортируйте нужные функции.

## Сценарии в своём приложении

Смотрите на места, где данные меняются или переходят между частями: пользовательский ввод, состояние попытки, ответ API, экран результата. Выберите поведение, при нарушении которого человек не сможет продолжить работу или получит неверное представление о результате. Для него назовите вход, действие и наблюдаемое ожидание. Конкретный сценарий зависит от устройства вашего проекта.

Для теста отдельного компонента можно подменить функцию API-клиента. В третьем тесте важно увидеть заголовок **сформированного HTTP-запроса**: если подменить функцию, которая сама добавляет `X-Access-Code`, тест этого не проверит. Задавайте ответы на уровне `fetch` или ниже места формирования заголовка. Реальный сервер в автоматических тестах не запускайте; проверяйте также видимое состояние, а не только вызов функции или внутренний setter.

## Async и очистка

Используйте `findByRole` или `waitFor`, только когда ожидаете изменение после асинхронной операции. Не добавляйте произвольный `setTimeout`. Перед каждым тестом очищайте только нужные mocks, а общий DOM очищайте `afterEach(cleanup)` из setup-файла. `globals: false` не отменяет необходимость cleanup.

## Разбор дефекта

Запишите четыре части: факт («после возврата текст исчез»), гипотеза («ответ привязан к позиции»), проверка (сценарий навигации) и исправление (выбранная модель связи). После исправления повторите исходный тест и один соседний сценарий. Не делайте вывод о всей системе по одному проходящему тесту.
